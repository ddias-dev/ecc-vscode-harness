## 1. Purpose

This document defines the architecture for the ECC Harness Adapter for VS Code.

The adapter acts as a bridge between:

```text
ECC Repository Assets
        ↓
ECC Harness Adapter
        ↓
GitHub Copilot
```

It provides a VS Code execution surface for ECC by discovering repository assets, assembling execution context, and dispatching structured requests to Copilot.

The adapter does not implement ECC workflows itself.

ECC remains the workflow definition layer.

Copilot remains the execution engine.

---

## 2. Architectural Principles

### P1. Repository-Driven

The adapter derives behaviour from repository assets.

The adapter must not hardcode:

- skills
- commands
- workflows
- project rules

Repositories remain the source of truth.

---

### P2. Convention Over Configuration

ECC assets should be discovered automatically.

Default experience:

```text
Open Repository
       ↓
ECC Assets Discovered
       ↓
Ready To Use
```

Minimal setup should be required.

---

### P3. Layer Separation

Each architectural layer has a single responsibility.

Example:

```text
Discovery Layer
    ≠
Context Layer
    ≠
Dispatch Layer
```

No layer should perform another layer's responsibilities.

---

### P4. Pluggable Asset Model

Future ECC asset types should be addable without redesigning the architecture.

---

### P5. Copilot Agnostic Core

Business logic should not depend directly on Copilot APIs.

Only the dispatch layer should contain Copilot-specific code.

This allows future execution surfaces.

## 4. Component Architecture

### Discovery Layer

Responsible for discovering ECC repository assets.

#### Responsibilities - Discovery Layer

```text
Locate ECC assets
Parse asset metadata
Build registry
Refresh registry
```

#### Inputs - Discovery Layer

```text
Workspace Files
```

#### Outputs - Discovery Layer

```text
ECC Asset Registry
```

---

### Context Layer

Responsible for collecting runtime information.

#### Responsibilities - Context Layer

```text
Selected code
Current file
Workspace information
Git context
```

#### Inputs - Context Layer

```text
VS Code APIs
Git Repository
Workspace
```

### Outputs - Context Layer

```typescript
ExecutionContext
```

---

### Prompt Layer

Responsible for constructing Copilot-ready requests.

#### Responsibilities - Prompt Layer

```text
Load skill
Load rules
Merge context
Build request payload
```

#### Outputs - Prompt Layer

```typescript
PromptPayload
```

---

### Dispatch Layer

Responsible for invoking Copilot.

### Responsibilities - Dispatch Layer

```text
Submit prompt
Open chat session
Handle execution results
```

### Outputs - Dispatch Layer

```text
Copilot Request
```

## 5. Domain Model

### Skill

Represents a reusable ECC workflow.

```typescript
export interface Skill {
  id: string;
  name: string;
  description: string;
  instructions: string;
  sourcePath: string;
}
```

---

### Rule

Represents project guidance.

```typescript
export interface Rule {
  id: string;
  title: string;
  content: string;
  sourcePath: string;
}
```

---

### Command

Represents an executable ECC action.

```typescript
export interface Command {
  id: string;
  name: string;
  description: string;
}
```

---

### Asset Registry

System-wide asset catalogue.

```typescript
export interface AssetRegistry {
  skills: Skill[];
  rules: Rule[];
  commands: Command[];
}
```

---

## 6. Context Model

The context engine generates the working context for execution.

```typescript
export interface ExecutionContext {

  gitBranch?: string;
  filePath?: string;
  language?: string;
  selectedText?: string;
}
```

## 16. Definition of Architectural Success

The architecture is successful when:

1. ECC assets are automatically discoverable.
2. New ECC skills require no code changes.
3. Context collection is isolated from dispatch logic.
4. Copilot integration is isolated behind a dispatcher.
5. Additional execution surfaces can be added without redesigning the core system.
6. All execution requests flow through a consistent registry → context → prompt → dispatch pipeline.
